# Meridian Analytics — Idempotency Pattern for Payment Processing

**Document ID:** doc_tech_idempotency
**Owner:** Payments Engineering Team
**Last updated:** 2026-07-02

## Overview

Meridian Analytics processes thousands of payment transactions daily across subscription billing, usage-based invoicing, and marketplace settlements. Network failures, client timeouts, and infrastructure disruptions cause legitimate retries of payment **API** calls. Without a robust **idempotency** mechanism, these retries risk duplicate charges, accounting discrepancies, and customer dissatisfaction. This document defines the idempotency pattern that all Meridian **payment processing** services must implement, including the handling of **idempotency key** within a 24-hour **retry** window.

## Idempotency Key Protocol

Every payment API endpoint at Meridian requires clients to provide an `Idempotency-Key` header on each request. The idempotency key must be a UUIDv4 string generated by the client. The key uniquely identifies a logical operation -- not the HTTP request itself. For example, a single payment authorization attempt that is retried three times due to network timeouts must use the same idempotency key on all three requests.

When a payment API receives a request with an idempotency key it has not seen before, it processes the request normally and stores the response (status code, headers, and body) indexed by the key combined with the target resource path. For subsequent requests with the same key within the 24-hour retention window, the service returns the cached response without executing the payment logic again. This ensures that the client can safely retry without side effects.

The response cache includes the original HTTP status code, so a previously failed payment that returned 402 Payment Required will re-return 402 on retry -- the system does not re-attempt processing. Only the client can provide a new idempotency key to initiate a fresh payment attempt.

## 24-Hour Retry Window Handling

When a client retries with the same **idempotency key** within 24 hours of the original request, Meridian's payment service follows this logic:

1. **Still processing** (no final response yet): Return HTTP 409 Conflict with `Retry-After: 5`.
2. **Completed with definitive response** (success or terminal failure): Return the cached response immediately.
3. **Failed with retryable error** (network error, 503, timeout) and payment gateway has not settled: The service reprocesses the request and updates the cached response.
4. **Succeeded but client never received response**: Return the cached success response.

## Cache Storage and Expiry

Idempotency key data is stored in a dedicated Redis cluster with 24-hour TTL (86,400 seconds), key prefix `idempotency:payment:`, and 256 KB storage limit per key. The 24-hour window is measured from the initial request timestamp, not from each subsequent retry.

## Error Recovery and Reconciliation

Despite the idempotency guarantee, Meridian runs a daily reconciliation process that cross-references payment API idempotency logs against bank settlement reports. Any charge that appears in settlement but has no corresponding idempotency key record triggers an investigation. This defense-in-depth approach has detected two upstream gateway bugs in the past year and ensures that the 24-hour idempotency window does not become a single point of failure for payment integrity.
